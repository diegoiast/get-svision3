# SVision3 documentation site

Static documentation site for [SVision3](https://github.com/diegoiast/svision3),
built with [Docusaurus](https://docusaurus.io/).

> This is the `docusaurus` branch. The `main` branch has a parallel MkDocs
> Material build of the same content — this branch is the newer,
> React/MDX-based rebuild, with an added blog.

## Install & run

```bash
npm install
```

Serve locally with live-reload:

```bash
npm start
```

Build the static site into `build/` (always run this before considering a
change done — it fails the build on broken links):

```bash
npm run build
```

Preview the production build locally:

```bash
npm run serve
```

## Project layout

```text
docusaurus.config.js             Site config, navbar, footer, GitHub Pages settings
sidebars.js                      Docs sidebar structure (mirrors the widget categories)
docs/
  tutorial.md                    Getting-started tutorial
  declarative.md                 Guide to the fluent declarative demo API
  widgets.md                     Widget/module index
  widgets/*.md                   One API reference page per widget
  assets/screenshots/            Per-theme widget screenshots (generated, see below)
blog/                            Blog posts
src/
  pages/index.js                 Hero/landing page (React, not Markdown)
  theme/MDXComponents.js         Registers <Tabs>/<TabItem> globally for every doc page
scripts/
  add_screenshots.py             Inserts/refreshes the screenshot galleries in docs/widgets/*.md
```

## Updating widget screenshots

Every widget page shows a themed screenshot gallery (`<Tabs>`/`<TabItem>`),
one tab per theme SVision3 ships (macOS, Material, Windows 11, Windows 95,
Plasma 6, GNOME). These are generated by a small headless tool that lives
in the **svision3** repo itself (not this one): `demo/widget_screenshot.cpp`,
built as the `widget_screenshot` CMake target. It renders each widget
offscreen — no display server needed — using the dummy platform backend
plus a Cairo image surface, and saves a PNG per `(widget, theme)` combination.

### 1. Build the tool

From the svision3 repo root (adjust the path to wherever you have it
checked out):

```bash
cd ../svision3
cmake --build build/Debug --target widget_screenshot -j"$(nproc)"
```

This assumes svision3's own Conan/CMake setup is already configured (see
its README). The tool only needs the `toolkit` library and its own source
file — no new dependencies.

### 2. Run it

Run it **from the svision3 repo root** — a couple of the demo widgets
(`image_widget`, `file_browser_widget`) load files using paths relative to
the current directory.

```bash
# Every widget, every theme — <output-dir>/<theme-slug>/<widget>.png
./build/Debug/widget_screenshot all /tmp/svision3-screenshots

# Just one widget, still across all themes (useful while iterating)
./build/Debug/widget_screenshot button /tmp/svision3-screenshots
```

### 3. Copy the output into this site

```bash
rm -rf docs/assets/screenshots
cp -r /tmp/svision3-screenshots docs/assets/screenshots
```

### 4. Refresh the galleries in the docs

```bash
python3 scripts/add_screenshots.py
```

This scans `docs/assets/screenshots/macos/*.png` for widget names and, for
each one, inserts (or replaces, if already present) a `<Tabs>` gallery
right after the intro paragraph on the matching `docs/widgets/<name>.md`
page. It's idempotent — safe to run again even if nothing changed.
`<Tabs>`/`<TabItem>` don't need a per-file import — they're registered
globally in `src/theme/MDXComponents.js`.

### 5. Rebuild and check

```bash
npm run build
```

### Adding a screenshot for a new widget

1. Add an entry for it to the `build_registry()` map in
   `demo/widget_screenshot.cpp` (in the svision3 repo) — it needs a small
   representative instance of the widget and a canvas size. Most entries
   use the `simple()` helper (stretches to fill the canvas) or `natural()`
   (renders at the widget's own natural size, for compact controls like
   buttons and inputs).
2. Re-run steps 1–5 above. `add_screenshots.py` will pick up the new PNG
   automatically and insert a gallery into `docs/widgets/<name>.md` — as
   long as that page already exists.

## Deploying to GitHub Pages

`.github/workflows/deploy.yml` builds and deploys to GitHub Pages on every
push to `docusaurus` (or whichever branch you set as the deploy source —
see the workflow file). It uses `actions/deploy-pages`, which needs Pages
enabled for this repo under **Settings → Pages → Source: GitHub Actions**.

Before deploying, double-check `url`, `baseUrl`, `organizationName`, and
`projectName` at the top of `docusaurus.config.js` — they're currently set
from this repo's local directory name and may need adjusting to match
wherever this actually gets pushed.
